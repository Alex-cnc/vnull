## 3. 「完全一致」的工程含义（这里必须说实话，否则排期会失真）

**这不是一个编译开关，而是「第二个客户端」。** 本工程是 **macOS 原生**（SwiftUI + AppKit 桥接）—— 今天实跑核实：

| 项 | 数值（2026-09-26 实测） |
|---|---|
| Core 源码 | 162 文件 / 39.7k 行（`Core/`，含 PostgresNIO 驱动适配） |
| App 源码 | 88 文件 / 27.9k 行（`App/`，SwiftUI + AppKit） |
| CLI | 4.9k 行 |
| 测试 | **1922 项，0 失败**（`./Scripts/verify-core.sh` 今天 07:03 实跑） |
| 门禁 | 11 项（`./Scripts/verify-all.sh` 今天实跑全绿，含打包 `.app`） |
| 需求 | FR 168 / NFR 43 / AC 12；等价矩阵覆盖 168 条 |

**好消息（可以直接复用、不用重做的部分）**：三书早就按「双平台产品规格」写好了，Windows 版正好落在它的设计意图里 ——

| 可复用资产 | 位置 | 为什么能复用 |
|---|---|---|
| 需求基线 + 验收标准 | SRS 全篇（需求只写产品行为，不写平台实现；严格档 0 处平台专属词） | 需求与验收标准与本工程语言无关，Windows 照抄 |
| 平台适配层**契约** | `概要设计.md` §3（连接配置 / 驱动 / 事件模型 / 结果模型 / 方言 / 元数据 / 终端屏幕 / 工作区 / 设计令牌 / 智能体治理 / 归档与记忆，每条给数据结构 + 不变量 + 跨平台验收点） | 契约层就是为「换实现不换行为」准备的 |
| **平台差异登记表** | SRS §10.9（P-01 ~ P-12：GUI 框架 / 凭据存储 / 目录授权 / 外部程序 / 终端 / 菜单 / 字体输入法 / 打包 / 剪贴板 / 更新 / 沙箱 / 系统集成） | Windows 的差异**照这张表逐条登记**，不会漏 |
| **平台等价矩阵**（机械生成） | SRS §10.10 + `Docs/平台实现状态.json` + `Scripts/gen-platform-parity.py` | 已有「状态不手工维护、由脚本重写表格」的机制；加一列就能看 Windows 的进度 |
| 设计令牌 | `Docs/design/外观方案-v1.md` + `Scripts/check-design-tokens.py` | 取值一致是可判定的（今天实跑：App 仍有 374 处待迁移，棘轮在守） |
| 两平台必备闸门 | `概要设计.md` §8.3 | Windows 侧从第一天就要有等价门禁，而不是事后补 |

**必须重做的部分**：Core 的业务逻辑（Swift 代码不能直接跑在 Windows 上）、全部界面、驱动接入（Npgsql / MySqlConnector 之类的等价替代）、凭据存储（Windows Credential Manager）、目录授权与沙箱模型、终端仿真、打包与签名。**门禁与测试矩阵也要在 Windows 侧重建一套** —— 「完全一致」的可验证性靠的是这条，而不是口头承诺。

**结论（一句话）**：`完全一致` 的可行路径是「**按契约重写一套原生实现**」（或「跨平台内核 + 各端原生壳」，但 Swift 内核跨不过去，等于内核也要重写）。工作量下限是**再做一个客户端**，上限取决于「一致到什么程度」——§10.9 那张表就是判据。

## 4. 需要你定的（记在这里，不弹窗）

| 编号 | 事项 | 选项与代价 | 我的建议 |
|---|---|---|---|
| **Q17** | Windows 版叫什么 | ① `Doyah Studio`（Windows）—— 与定位一致，但「Doyah Notes」这个刚定的名字就要收回给移动端独占；② 保留 `Doyah Notes` —— 名不副实（它不再只是笔记） | **①**，移动端保留 `Doyah Notes` |
| **Q18** | Windows 版是否也分 Ultra / Standard 两档 | ① 与 macOS 一致分两档（license 能力位照用）；② Windows 只有一档（全功能） | **②**：Standard 的动机是「同一台 Mac 上不出现数据库入口」，Windows 机上没有这个问题；先一档，将来要分再分 |
| **Q19** | Windows 版排在哪个里程碑 | ① 紧跟 M1.5（Standard）之后；② 排在 M3（与移动端并列，即现状顺延）；③ 暂不排，先把 macOS 做出可交付版本 | **③ → ②**：macOS 侧仍有 68 条需求未完结（其中 4 条真未动、其余待人工/待实例），Windows 现在开工会双线失血；建议**在 macOS 达到「人工验收清零」后再启动 Windows 侧**，并用 §10.10 加一列跟踪 |

**另一条必须同时确认的**：本次指示**只说 Windows**。移动端（鸿蒙 / 安卓 / iOS）是否仍然是「只有笔记」？我按「不变」处理了 —— 若你要一并改成完全一致，代价还要再乘三（三端各一套原生实现）。

## 5. 我建议的落地顺序（Windows 侧启动时照这个走）

1. **先把机械设施扩到三平台**：`Docs/平台实现状态.json` 增加 `windows` 键，`Scripts/gen-platform-parity.py` 从「macOS × Linux 两列」扩为「macOS × Linux × Windows × 移动端」多列 —— 这样「完全一致」从第一天就是**可判定的**，而不是靠人记。
2. **按 `概要设计.md` §3 的契约逐条落地**，先做只读链路（连接 / 元数据 / 查询 / 结果网格 / 导出），与 Linux 侧的起步顺序相同（那份顺序是现成的）。
3. **§10.9 差异登记表逐条登记**，每一条写清「为什么必须不同 + 用户可感知的差异」。
4. **等价门禁先于功能**：Windows 侧要有一套与 `verify-all.sh` 等价的闸门（Core 单测 / 平台中立性 / 令牌 / 文档计数 / 状态一致性 / 打包），否则「一致」无从判定。

> 第 1 步是纯机械工作、今天就能做，而且是后面所有工作的前提。**要不要我现在就做**（给等价矩阵加 Windows / 移动端两列），见 §6。
