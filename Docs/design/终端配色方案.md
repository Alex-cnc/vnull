# 终端配色方案（FR-EDIT-29）

> 一句话：终端以前是**视图里 16 个手写 `NSColor`**，深色下大半不可读、浅色下更糟；
> 现在是一份**带门槛的调色板**（`Core/TerminalPalette`，深 / 浅两套），
> 对比度与可区分性由 `TerminalPaletteTests` 与 `Scripts/test-terminal-palette.sh` 守着。
>
> **这份文档同时是跨平台交接物**：Linux 侧要按同一套配色实现自己的终端 —— 色值以
> `Docs/design/terminal-palette.json`（机器可读，由 Core 机械导出）为准，本文是它的人读版。
> 三者由 `Scripts/check-terminal-palette.py` 钉在一起（接在 `verify-all.sh` 第 3 项里），
> 改色板就必须同时更新 JSON 与本文，否则门禁会失败。

## 1. 为什么改：旧色板量出来的问题

旧色板在视图里硬编码，且**深浅两种外观共用同一套**。实测（WCAG 对比度，脚本可复算）：

| 场景 | 旧色板的实际表现 |
|---|---|
| 对 app 深色底 `#1F2229` | 黑 **1.3**、蓝 **2.6**、红 **2.9**、品红 **3.2** —— 四处低于正文门槛 4.5 |
| 对浅色（白底） | 绿 **3.2**、黄 **2.5**、青 **3.1**、白 **1.6**；八个亮色槽全线 **1.1 ~ 3.3** |

也就是说：**深色档的蓝红发灰、浅色档的亮色基本看不见**。旧实现里那句注释
"ANSI 色板是终端语义，不能改"只对了一半 —— 序号语义不能改（1 必须是红），
**但"红是哪一种红"必须按底色重新设计**，否则颜色传达到了，字却读不出来。

## 3. 三条规矩（单测钉着，不是形容词）

1. **可读**：当正文用的槽位对底色 **≥ 4.5**（WCAG AA）；前景对底色 **≥ 7**（AAA）；
   选中底上写字 **≥ 7**；光标对底色 **≥ 3**。
2. **可区分**：不同色相之间 ΔE ≥ **25**（红不能看着像橙）；同一色相的"常规 / 亮"两档 ΔE ≥ **8**。
3. **背景槽的例外**（四个，写清楚免得被当成漏网）：
   - 深色档的黑 / 亮黑：纯黑在深底上不可见，所以黑槽被抬到 `#2B303C`；
     要求**与底色 ΔE ≥ 8**（当背景时看得出边界）；
   - 浅色档的白：是一块**浅灰**（与底色 ΔE ≥ 5），程序拿它当背景时看得见；
   - 浅色档的亮白：**按设计就是白**（与底色 ΔE ≤ 3）。这是行业惯例（Solarized Light 的 base3、
     GitHub Light 的 `#fafbfc` 都贴着底色）："白底上画白底"是程序自己的选择，不替它改。

**已知最紧的一处**：浅色档的黄（常规 `#7E5500` 6.38 / 亮 `#926200` 5.12，同色相 ΔE 仅 **8**）——
近白底上"更亮的黄"必然掉对比度，这一档已经贴着两条门槛的交界。要再拉开 ΔE 就得动色相，
那会让"黄"不再是黄，所以停在这里并写进本文件与单测注释。

## 4. 渲染口径（不只是"选颜色"）

| 行为 | 做法 | 为什么 |
|---|---|---|
| **跟随系统外观** | 深 / 浅两套色板按 `effectiveAppearance` 取；换外观时清掉按行属性缓存并重画 | 一套色板在另一套外观里必有一半不可读（旧实现就是这个毛病） |
| **外观可覆盖（三态）** | 「跟随系统 / 总是深色 / 总是浅色」（`TerminalAppearance`，纯函数 `resolvesToDark(systemIsDark:)`） | 长时间看 shell 输出时，很多人愿意在浅色界面里配深色终端；覆盖态**不受系统外观影响**，单测钉住 |
| **字号可调** | 9…20 pt（`TerminalFontSize`，夹取在 Core；默认 12 = `TypeScale.monoSize`）。改动会**重建字体与格子尺寸并重新布局** | 拿旧格子宽度反算列数会把 120 列报成 80 列，TUI 第一帧就排错；上下限防"小到糊 / 大到一行放不下几个字" |
| **粗体提亮** | `bold` + 索引色 0…7 → 用 8…15 | xterm 老习惯；`ls` / `grep` 只发 `1;3x`，不提亮就是一片同色粗体。常量在 `TerminalPalette.brightensBold`，便于日后关掉 |
| **暗淡（SGR 2）** | 前景按 55% 混进底色（`dimmed`） | 比"降透明度"稳：透明度叠在别的底色上会变味 |
| **`1;2` 并存** | 先提亮再压暗 | 两者不是互斥开关 |
| **SGR 22** | 粗体**与暗淡一起清** | 标准如此；只清一半会留下"暗的粗体" |
| **反显** | 前景↔背景成对交换（显式着色时交换那一对） | 交换的是"本来那一对"，不是交换成默认色 |
| **块状光标** | 实心块 + **把块内的字用底色重画**（反白） | 半透明块让字符发脏；真终端里块光标下就是反白的 |
| **失焦光标** | 只描一个 55% 的空心框 | 块状光标在失焦窗口里会显得"这里还能打字" |
| **选中** | 不透明选中底（深 `#24304A` / 浅 `#D8E3FF`） | 半透明叠加后又是一个没算过对比度的颜色 |

256 色立方与灰阶按 xterm 标准（`16…231` 步长 `0/95/135/175/215/255`，`232…255` 是 `8 + n×10`），
真彩色原样透传 —— 这部分以前在视图里手写，现在搬进 Core 并单测（`resolve`）。

## 5. 怎么验

```bash
./Scripts/test-terminal-palette.sh      # 构建 + 色板输出 + 独立复算门槛 + 外观三态 / 字号夹取 + 单测
./.build/debug/DoyahCLI terminal-palette        # 看两套色板（人读表）
./.build/debug/DoyahCLI terminal-palette --json # 给脚本用（同一份事实源）
./.build/debug/DoyahCLI terminal-palette --appearance alwaysLight --system dark   # 看覆盖态
```

脚本特意**用两份实现算同一件事**：单测用 Swift 的 `contrastRatio`，脚本读 CLI 的 JSON
用 Python 再算一遍 —— 两边都给出"全部 ≥ 4.5"才算这条门槛成立。

## 6. 在界面里怎么改

「显示 → 外观…」面板底部新增「终端」一段（`App/Views/AppearanceSheet.swift`）：

- **配色**：跟随系统 / 总是深色 / 总是浅色（分段控件），选完立即生效；
- **字号**：9…20 pt 的 Stepper（标签实时显示当前值），改动会重建网格并让 shell 重新分栏；
- **字体族**：来自面板上方「字体（等宽）」那一段（FR-EDIT-26）—— **族全局共用**（编辑器与终端字形一致），
  **字号各有各的**（与 VS Code 的 `terminal.integrated.fontFamily` / `fontSize` 同一分工）；
- **预览**：用**真实色板**画的一小块终端（提示符 + 8 常规 + 8 亮色 + 暗淡 / 选中 / 光标），
  不让用户凭想象选配色。预览的底色、前景、选中底、光标全部取自同一份 `TerminalPalette`。

两项目都持久化在 `UserDefaults`（`terminal.appearance` / `terminal.fontSize`），
未知值分别回落「跟随系统」与默认字号 —— 偏好被手改也不会让终端起不来。

命令行同样能复算（`--system` 用来模拟系统外观，证明覆盖态不受它影响）：

```bash
doyah terminal-palette --appearance alwaysDark --system light   # → 深海·夜
doyah terminal-palette --font-size 100                          # → 夹到 20 pt
```

## 7. 给 Linux 版本（跨平台交接）

同一套配色在两个平台上**必须一致**（SRS §10.9 已登记）：一致的是**色值本身与门槛**，
允许不同的是渲染实现（AppKit 的 `NSAttributedString` vs 你们的文本栈）。

**权威来源**（按优先级）：

1. `Docs/design/terminal-palette.json` —— 机器可读，**hex 是权威**。结构：
   ```json
   [
     { "kind": "resolution", "appearance": "followSystem", "fontSize": 12, ... },
     { "kind": "palette", "name": "深海·夜", "isDark": true,
       "background": "#14171E", "foreground": "#D6DBE4",
       "cursor": "#6E8BFF", "selection": "#24304A",
       "foregroundContrast": "12.90",
       "ansi": [ { "index": 0, "name": "black", "hex": "#2B303C",
                   "contrast": "1.36", "backgroundSlot": true }, ... ] }
   ]
   ```
   用 `kind` 筛选（别靠"有没有某个键"猜）；`contrast` 是**两位小数的字符串**，
   只为可读与 diff 稳定，不要拿它当数值参与计算 —— 要算就用 CIELab/WCAG 自己算。
2. 本文的表（同一批色值的人读版）。
3. 重新导出（改了色板之后）：`python3 Scripts/check-terminal-palette.py --write`。

**必须照抄的语义**（不只是颜色）。每条都标了它的**出处**，好让你判断"能不能改"：

| # | 语义 | 出处 | 能不能改 |
|---|---|---|---|
| 1 | ANSI 序号：1 红、2 绿、3 黄、4 蓝、5 品红、6 青、7 白；8–15 是对应亮色 | **标准惯例**（SGR `30–37` / `40–47`、`90–97` / `100–107`） | 不能 —— `ls` / `grep` / 测试框架都按这个序号发色 |
| 2 | 四个"背景槽"例外（深色档 0/8、浅色档 7/15，见 §3） | **本项目规则**（`TerminalPalette.isBackgroundSlot` + 单测） | 可以谈，但要两边一起改并登记（§10.9） |
| 3 | 粗体提亮：索引色 `0–7` + 粗体 → 用 `8–15` | **惯例但非强制**（xterm 老习惯；kitty 等把它做成开关） | 可以关 —— 代价是 `ls --color` / `grep --color` 的强调会变成"同色加粗"。本项目的常量是 `TerminalPalette.brightensBold`，要改两边一起改 |
| 4 | 暗淡：前景按 55% 混向底色（`dimmed`） | **本项目规则**（SGR 2 只说"faint"，具体比例由实现定） | 比例可以谈（我们取 55%），但**必须仍然看得出有字**（单测有下限） |
| 5 | `1;2` 并存（先提亮再压暗）；**SGR 22 同时清粗体与暗淡** | **标准惯例**（SGR 22 = normal intensity，ECMA-48 语义） | 22 不能只清一半，否则会留下"暗的粗体" |
| 6 | 反显：前景↔背景**成对交换**（显式着色时交换那一对） | **标准惯例**（SGR 7 / 27） | 实现细节可以不同，但"交换哪一对"不能变 |
| 7 | 256 色立方取整 `0/95/135/175/215/255`、灰阶 `8 + n×10`（`232…255`） | **标准惯例**（xterm 的 256 色定义） | 不能 —— 取整不同则同一程序在两边颜色不同 |
| 8 | 两档外观（深 / 浅）都要有，且各自满足 §3 的门槛 | **本项目规则**（门槛数值见 §3） | 门槛可以谈，但"两档都要有"是需求（浅色界面里也能一眼看清） |

**对照结果（2026-09-24 逐条核对 [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.txt)，它以 ECMA-48 / ISO 6429 为底本）**：

| 清单条目 | 核对结果 |
|---|---|
| 1（ANSI 序号） | **对上**：`Ps = 30…37 -> Set foreground color to Black/Red/Green/Yellow/Blue/Magenta/Cyan/White`（`40…47` 同理是背景）。但要分清来源：**30–37 是 VT100/ECMA-48**，而 `90…97` 是 **aixterm 扩展**（文档原话：*"If 16-color support is compiled, the following aixterm … the aixterm colors are the bright versions of the ISO colors"*）—— 也就是说"亮色"这一档不是 ECMA-48 的东西，别按标准正文去找 |
| 3（粗体提亮） | **规范里没有这条**：ctlseqs 只定义 `Ps = 1 -> Bold`，没有任何"粗体要用亮色槽"的要求。所以它确实只是终端实现的惯例（kitty 等做成开关）—— 清单原来的标注是对的 |
| 5（`1;2` 并存、22 清两者） | **对上且升级为条款级**：`Ps = 2 -> Faint, decreased intensity, ECMA-48 2nd`、`Ps = 22 -> Normal (neither bold nor faint), ECMA-48 3rd` —— 我们的实现正是"22 同时清粗体与暗淡" |
| 6（反显成对交换） | **对上**：`Ps = 7 -> Inverse, VT100`、`Ps = 27 -> Positive (not inverse), ECMA-48 3rd` |
| 7（256 色取整） | **需要分清**：`0/95/135/175/215/255` 与 `8 + n×10` 是 **xterm 的 256 色调色板布局**，ctlseqs 里并没有写这组数字（它只说 xterm 维护一张调色板）。真正有规范依据的是**取色的写法**：`38:5:Ps`（索引色）与 `38:2:Pi:Pr:Pg:Pb`（真彩色）出自 ISO-8613-6，ECMA-48 5th 把它们标为 *"reserved for future standardization"*；分号写法 `38;5;Ps` / `38;2;Pr;Pg;Pb` 则是 xterm **为兼容 KDE konsole** 额外接受的 |
| 2 / 4 / 8（本项目规则） | 规范层面确认"可自定"：ctlseqs 对 `Ps = 2` 只说 *"Faint, decreased intensity"*，**没有规定降到多少** —— 我们取 55% 属于实现自由；对比度门槛与背景槽例外纯属本项目规则 |

**这次核对抓出并修掉的一个真缺口**：`38` / `48` 的**冒号写法**（`38:5:n`、`38:2::r:g:b`）原先**整段被忽略**（颜色静默丢失），而它是 ISO-8613-6 的正规写法、现代程序（编辑器等）确实会发。
`Core/TerminalScreen.swift` 现已同时支持两种写法（含带空颜色空间标识的 `38:2::r:g:b`），并补了 6 项单测（`TerminalExtendedColorTests`）。
教训：**光看"我们自己的实现"不会发现这种缺口** —— 差异只在跟规范对一遍时才暴露出来。

**这份清单是怎么来的**（说清出处，免得它看起来像"标准原文"）：

1. **实现现状**：清单里的每一条，都能在本仓的 `Core/TerminalPalette.swift`、
   `Core/TerminalScreen.swift`（SGR 解析）、`App/Views/TerminalView.swift`（渲染）里
   找到对应函数或分支；256 色立方与灰阶的取整算法本来就在视图里，本轮搬进 Core 并加了单测。
2. **标准惯例**：SGR 序号、`22` 的语义、反显、扩展颜色写法这些按 [xterm 的控制序列文档](https://invisible-island.net/xterm/ctlseqs/ctlseqs.txt)
   （它以 ECMA-48 / ISO 6429 为底本）的通行定义实现。**2026-09-24 已逐条核对过**（见上面的「对照结果」表）：
   第 1 / 5 / 6 条对上，第 3 条确认"规范里没有"（是惯例），第 7 条要把"调色板布局"与"取色写法"分开看。
   **仍需保留的一句实话**：核对的是 xterm 的控制序列文档，**没有去读 ECMA-48 标准正文本身**
   （那是付费标准，仓里也没有）；若你要引用到条款号级别的合同文本，建议再对着 ECMA-48 原文核 `22` 与 `38/48`。
3. **本项目规则**：对比度与可区分性门槛（§3）、四个背景槽的例外、暗淡比例 —— 这些是我们定的，
   单测钉着；要改就两边一起改，并在 §10.9 登记差异。

**改哪一条会破坏等价**：第 1、6、7 条改了 = 同一程序在两边显示不同颜色（用户可见的不一致）；
第 3、4、5 条改了 = 强调与弱化的观感不同；第 2、8 条是我们可以协商的产品口径。
