# 笔记正文格式调研（Q8 决策依据）

**目的**：在拍板 Q8「笔记正文的**权威源格式**」之前，把主流产品的做法查清楚，避免我们凭空选。

**问题定义（先说清 Q8 到底在问什么）**：一条笔记的正文会出现在四层，**这四层格式可以不同**：

| 层 | 作用 |
|---|---|
| ① 编辑态模型 | 编辑器内存里的形状（鸿蒙 `RichEditor` 的 span 树 / macOS `NSTextView` 的 attributed string） |
| ② **本地持久化（权威源）** | **谁是事实源**：重启后照着它重建 |
| ③ 云端同步载荷 | 上传什么（通常是 ② 的序列化；也可只传差量） |
| ④ 导出交换格式 | 给别人/别的工具（Markdown、HTML 片段、PDF） |

**Q8 = 选 ②**。③ 一般是 ② 的派生（**建议不要一开始就让 ②≠③**：那会在"合并后写回本地"处引入有损转换）。

**本文的置信度标注**：`【官方】`= 官方文档/规范；`【二手】`= 第三方总结/博客；`【认识】`= 我的既有认识、**本次未逐条核实**。
凡 `【认识】` 的条目在写进正式设计前都要复核（本节末列出复核清单）。

---

## 一、六条主流路线

### 1. 印象笔记：自有富文本 XML（ENML）+ 资源分离 + USN + 冲突副本
- 正文是 **ENML**：一个 XHTML 子集（`<en-note>` 根、受控的元素/属性白名单、自有 DTD）。资源（图片/附件）**独立存储**，正文里用 `<en-media hash=…>` 引用。【认识】+【二手】（见出处 [1]）
- 同步以**每账号更新序号（USN）**为依据：某端落后就拉增量；**同一笔记两端都改 → 不自动合并，生成"冲突副本"**。【认识】
- 对我们最有参考价值的两点：**资源分离**、**冲突宁可留副本不静默合并**。

### 2. Notion：块模型 + 块内富文本 span 数组
- 一条笔记是**有序的块集合**；每块有类型（段落/标题/列表/代码…）与属性；富文本是块内的 **span 数组**（文字 + 标注 annotations）。【二手】（见出处 [2]）
- 同步传**块级/属性级变更**，因此冲突粒度天然是"块/属性"；代价是**模型复杂、导出与 AI 改写都要先解引用**。【认识】

### 3. Obsidian / Logseq / Joplin：**文件即真相**，索引是派生
- 磁盘上的 `.md`（Logseq 也可 `.org`）就是权威源；数据库/索引只是**派生缓存**，删掉可重建。【二手】（见出处 [3]）
- 冲突：文件同步层产生**冲突副本**（`xxx (conflicted copy).md`），不静默合并。【认识】
- Joplin 另有 **JEX**（JSON 全量导出）作为迁移/备份载体，并支持多同步后端（WebDAV/Dropbox/S3/自建）。【二手】（见出处 [4]）

### 4. 苹果备忘录 / Craft 一类：私有 protobuf / 专用容器
- 正文以**私有二进制**（protobuf 等）存于本地库，跨端靠系统云 + 记录级冲突。**不可被外部工具直接读写**。【认识】
- 参考价值低（我们不打算放弃"可被别的工具读写"这条）。

### 5. CRDT 一类（Anytype 等）
- 用 CRDT 做**自动合并**，不再有"冲突副本"。代价：元数据体积显著上升、调试与迁移复杂、导出需投影。【认识】

### 6. 纯 Markdown + 旁挂样式（少见，但有先例）
- 正文 Markdown 为源，少量富样式以**旁挂元数据**（frontmatter / 侧车文件 / 行内自定义标记）保存。取舍见第三节。

## 二、对照表

| 维度 | ENML（印象） | 块模型（Notion） | 文件为源（Obsidian/Logseq/Joplin） | 私有 protobuf（Apple） | CRDT |
|---|---|---|---|---|---|
| 权威源 | 富文本 XML | 块 + span | **Markdown 文件** | 私有二进制 | 操作图 |
| 富样式能力 | 强 | 强 | **弱（受限）** | 强 | 强 |
| 外部可读写 | 需专用工具 | 需 API | **任意编辑器** | 不可 | 需专用工具 |
| 冲突策略 | 冲突副本 | 块级合并 | **冲突副本** | 系统级 | 自动合并 |
| 附件 | 分离存储 | 独立块/文件 | 独立文件 | 内嵌 | 独立块 |
| 迁移 | 自有 DTD | 表结构演进 | **纯文本，天然可迁移** | 黑盒 | 版本化 schema |
| AI 友好度 | 中（要解析 XML） | 中（要解引用） | **高（纯文本）** | 低 | 低 |
| 实现成本 | 中高 | **高** | **低** | — | 很高 |

## 三、三条比"选哪种格式"更重要的规律

1. **没有一家靠单一格式打天下**：都是「**一个权威源 + 若干投影**」（编辑器各自投影、导出各自投影）。所以我们真正要定的是**权威源**，而不是"统一格式"。
2. **资源（图片/附件）必须与正文分离**：正文只引用资源 id。对同步流量、冲突粒度、导出体积的影响，**比正文格式本身更大**。
3. **冲突处理的主流选择是"保留两版"，不是自动合并**（印象笔记、Obsidian、Logseq、Joplin 都是）；只有上 CRDT 才自动合并，而那要付复杂度与元数据体积的代价。这与我们既定的 Q4 倾向一致。

## 四、对 Doyah 的建议（选项 C 的细化版）

**建议：Markdown 为权威源 + 受限样式旁挂 + 资源分离 + 正文版本号 + 投影层放 Core。**

| 决定 | 内容 | 理由 |
|---|---|---|
| 权威源（②） | **Markdown**（+ 一条笔记级的样式侧车，仅在 Markdown 表达不了时使用） | 可 diff / grep / 被任意工具读写；与本工程既有 `CodeSyntax`/`CodeLexer` 及工作区编辑器同源 |
| 同步载荷（③） | 与 ② **同格式**（+ 版本号 + 附件分开传） | 避免"合并后写回本地"引入有损转换（Q3/Q4 的实现复杂度因此显著下降） |
| 编辑器投影（①） | 由 **Core 的纯函数**做 `Markdown ⇄ span 树` 投影，三端共用 | 鸿蒙 `RichEditor` / iOS / Android 各自只实现"渲染 span 树"；投影规则只有一份 |
| 资源 | **独立存储**（附件表 / 独立对象），正文只留引用 | 与印象笔记、Logseq、Joplin 一致；同步与冲突粒度都受益 |
| 冲突（Q4） | **保留两版**（人读得出差异，因为源是文本） | 主流做法；CRDT 留到确有需求 |
| 导出（④） | Markdown（默认）/ 社交平台用 HTML 片段 / 全量 JSON（备份） | 与 Studio 既有 md/docx/xlsx 写入器互补 |

**明确的代价与"不做"清单（必须写进需求书，否则以后会被反复要求）**：
- **不支持任意富文本**：行内底色、任意字号、复杂嵌套表格等**不做**（Markdown 表达不了就不做，而不是偷偷塞进侧车）；
- 样式侧车**只能承载"Markdown 的子集外"的少量属性**，并且**必须在导出 Markdown 时给出明确的降级规则**（例如颜色丢弃并提示）；
- 因此移动端的富文本工具栏会**比印象笔记窄**——这是自觉的取舍，不是实现不到位。

**若最终选 A（纯 Markdown）**：更简单，但行内颜色/字号一律没有，移动端体验会"素"。
**若最终选 B（span JSON 为源）**：富样式最强，但代价是：AI 改写要解引用、冲突合并复杂、外部工具不可直接读写、迁移需自建版本化 schema。
