# 笔记模块独立性评估（任务 3 回答）

| 项 | 值 |
|---|---|
| 写作者 | 大河马（hermes 侧开发助理） |
| 日期 | 2026-09-26 |
| 问题（需求提出者原话） | 「功能规划书里的笔记部分是否要独立出来，因为需要同步给移动平台保持一致，但移动平台又不需要 Studio 的能力」 |
| 结论 | **要独立，而且已经独立了一半**。剩下的一半是 **App 装配层**，不是数据层 |

---

## 1. 结论先给

三层要分开看，混在一起就会把「要不要独立」变成说不清的问题：

| 层 | 现状 | 判断 |
|---|---|---|
| **数据与模型层**（`Core/Note.swift`、`Core/NoteBody.swift`） | 已独立：不引用任何数据库 / 平台类型 | ✅ 已到位 |
| **许可与呈现层**（`Core/License*.swift`） | 已独立（签名校验用 swift-crypto，不依赖 Apple 专有 API） | ✅ 已到位 |
| **AI 产物写入笔记**（`Core/AICapture.swift`） | **已拆分完成**：`AICapture.swift` 只保留「标题 / 正文 / 来源」的笔记侧映射，诊断 / 维护的适配搬到了 `Core/AICaptureUltra.swift` | ✅ 已到位 |
| **App 装配层**（`App/AppState.swift` × 笔记状态与方法） | **未独立**：笔记的状态与增删改查长在 `AppState` 里，而 `AppState` 同时握着数据库侧 | ⬜ 要做，见 §3 |
| **跨端契约**（同步元数据 / 冲突语义 / 序列化） | 只有 `NoteBody` 的版本号与迁移规则；同步要用的字段（变更时间 / 设备 / 冲突标记）尚未定义 | ⬜ 属 M2（Q3/Q4 已拍板 CRDT，但契约未落文） |

所以对你这句话的回答是：**要独立，但「独立」的正确边界不是「把界面切出去」，而是「让笔记那一块能在不认识数据库的前提下被装配起来」。** 移动端要的是**模型与格式**，不是 Studio 的界面能力 —— 界面本来就不共享（各端原生）。

## 2. 为什么必须独立（三条理由，第三条是新增的）

1. **移动端是独立应用**：`Doyah` / `Doyah Notes`（鸿蒙 / 安卓 / iOS）打包时不能背着数据库代码与驱动依赖 —— 这是体积、许可与安全边界问题，不是洁癖。
2. **macOS 两版仍需要「只装配笔记」的能力**：Q9 已关闭（Ultra / Standard 同一个 app、同一个数据家，Standard 只屏蔽活动栏两项），但屏蔽是**界面层**的事；构建与依赖的干净度、以及「笔记功能不被数据库侧改动带崩」仍要有边界。
3. **AI 结合点天然要穿过这条边界**：诊断结论 / 维护计划 / SQL 写法要能沉淀成笔记（DOYAH-09/10）。这条边界画错，AI 产物就会把 Ultra 侧的类型（`DiagnosisContext`、`MaintenancePlanReview`）拖进笔记模块 —— 这个坑项目里已经踩过并修好了（`AICaptureUltra` 那次拆分）。

## 3. 还差什么：三处，都有具体落点

### 3.1 App 装配层未解耦（唯一的真缺口）

机器上实测（2026-09-26）：

- `App/AppState.swift` **6344 行**，同时持有笔记与数据库两侧状态；
- 笔记相关引用：第 **338** 行 `@Published var notes: [Note]`、第 **5901** 行 `visibleNotes`、**5922** `load`、**5928** `beginNewNote`、**5935** `edit`、**5973** `deleteNote`、**6098** `saveMaintenanceNote`、**6266** `saveDiagnosisNote`；
- 唯一的笔记视图 `App/Views/NotesPanel.swift`（4.8 KB）通过 `@EnvironmentObject AppState` 取数据 —— 也就是说**想要「只有笔记」的装配，就得把整个含数据库侧的 `AppState` 一起带进包里**。

这一条在门禁脚本自己的注释里也被点名（`Scripts/check-note-module-isolation.py` 的「已知未覆盖」段落），不是我发现的新问题，但**它至今没有排期**。

### 3.2 门禁的白名单式扫描不够硬

现行门禁按**文件白名单**扫（`NOTE_SOURCES` 四个文件）。它能证明「这四个文件干净」，**不能证明「笔记模块的依赖闭包干净」** —— 新增一个笔记源文件而忘记登记，门禁照样全绿。

### 3.3 跨端契约未落文

`NoteBody` 已有版本号与迁移规则（这是好底子），但**同步要用的元数据没有定义**：变更时间、删除墓碑、设备标识、冲突标记、字段级合并的粒度。Q3/Q4 已拍板（CRDT + 逐字段合并），但契约没写下来 —— M2 开工前必须落文，否则三端各写一套「同步格式」。

## 4. 建议的切法（三步，S1 现在就能做）

| 步骤 | 内容 | 判据（机器可验） |
|---|---|---|
| **S1** | 把笔记状态与方法从 `AppState` 抽到 `App/NotesModel.swift`（`ObservableObject`）；`NotesPanel` 改为依赖 `NotesModel`；`AppState` 只保留「AI 产物 → 草稿」的 Ultra 侧调用 | 门禁扫描范围扩大到 `App/NotesModel.swift` + `App/Views/NotesPanel.swift`（禁 `AppState` / `DatabaseService` / 方言类型引用）；`verify-core.sh` 全绿 |
| **S2** | 把笔记抽成独立构建单元（SwiftPM target，例如 `DoyahNotesCore`），由 `Core/Note*.swift` + `AICapture.swift` + `License*.swift` 组成；门禁改为**扫 target 的依赖闭包**而不是文件白名单 | `swift build --target DoyahNotesCore` 只依赖 Foundation；门禁对「新增文件忘记登记」免疫 |
| **S3** | 写跨端契约（数据模型 + 序列化 + 同步元数据 + 冲突语义），落 `Docs/概要设计.md` §3 的【契约】区；移动端按它实现 | 契约条目能被三端各自写出等价测试；笔记格式跨端读得通（`NoteBody` 版本号已具备） |

**代价与边界（先讲清，免得后面被当成缺陷）**：

- **界面不共享**：S1/S2 只让「模型 + 逻辑 + 许可」独立，笔记界面仍是各端原生（PC 与移动端设计本就不同）。
- **三条安全边界要跟着模块走**（DOYAH-09/10/11）：默认不存结果集行数据（要存须显式勾选 + 过脱敏，并在笔记元信息里留痕）、口令与带口令的连接串永不入库、同步出网纳入统一外发日志（NFR-SEC-08）。脱敏与出网留痕都在 Ultra 侧，**抽模块时不能把它们留在原地**。
- **S1 会碰 6344 行的 `AppState`**：改动是「搬出去 + 转发」，不做结构调整；`AppState` 被约百处引用，动它就等于动全局，所以必须一次只做一件事、每步跑门禁。

## 5. 顺带纠正一处口径（供你确认）

现行文档里「笔记模块必须完全解耦」的理由写的是 **「Windows / 移动端的 Doyah Notes 是独立应用，不能背数据库代码」**。今天你给了新口径 —— **Windows 版与 macOS 版完全一致**（见 `Docs/design/Windows-完全一致-口径变更与影响-20260926.md`）—— 那么：

- 这条理由里的 **Windows 部分不再成立**（Windows 版将来是全功能的 Studio，本来就要数据库侧）；
- 但结论**不变**：移动端 `Doyah Notes` 仍是独立应用，解耦照做；macOS 侧的装配边界照做。

也就是说：**指示变了，工程动作没变，只是理由少了一条。**
