## 1. 产品定位与不可让渡的原则

**定位**：原生、轻量的数据库工作台；把**智能体**作为一等能力内置，但**默认关闭、每一步看得见、可审批、可审计、绝不自动执行**。

同一个产品做**两个平台实现**：macOS 版（本仓库）与 Linux 版（公司电脑），功能一致，只有平台与编程语言不同 —— 口径见 §1.1（P7）。

若与竞品（如 DataGrip 的 AI 能力、各类 MCP 数据库网关）比较，本产品的差异化**不在模型更强，而在「敢用」**：每一步都能被证明与追责。

| # | 原则 | 含义 | 依据 |
|---|---|---|---|
| P1 | **治理优先** | 显式同意、最小外发、权限继承当前连接、写操作逐次审批、审计留痕 —— **缺一条不上线** | NFR-AI-01 / 03 / 05、FR-AI-09、FR-AI-12；调研书结论「安全边界是协议层与产品层的硬约束」 |
| P2 | **可降级** | 无模型 / 未授权 / 断网时，**全部既有功能完整可用** | NFR-AI-02 |
| P3 | **本地模型优先 / 默认零外发** | 支持 OpenAI 兼容本地端点且免 Key；默认配置即「总开关关闭 + 端点为空」 | NFR-AI-06、NFR-AI-02 |
| P4 | **真实数据接地** | 诊断类能力必须站在真实执行计划 / 锁等待 / 统计之上，不做"没有依据的建议" | FR-DIAG-01、FR-DIAG-05、FR-SESS-01 |
| P5 | **可复核** | 智能体产出（SQL / 任务定义 / 建议）都以文本可查看、可编辑、可 diff | NFR-AI-05 |
| P6 | **原生轻量** | 无 JVM / 无 Electron；不为功能引入重量级运行时 | 1.2 产品目标 |
| P7 | **双平台等价** | macOS 与 Linux 是**同一个产品的两个实现**：能力清单、行为语义、验收标准一致；差异只允许出现在「平台适配层」以内，并且**逐条登记、可查、不可悄悄有** | SRS §0.8、§10.9、§10.10；概要设计 §3 平台适配层契约 |

## 1.1 双平台等价（P7 的落地口径）

### 1.1.1 什么算「一样」

| 维度 | 要求 | 判定方式 |
|---|---|---|
| **能力清单** | 两侧需求条目集合一致（数量与编号对应） | SRS §10.10 等价矩阵，由 `Scripts/gen-platform-parity.py --check` 强制 |
| **行为语义** | 契约级不变量一致：取消必须传到执行端且双向生效、受影响行数只报一次、结果截断必须可见、写操作逐次审批、密钥不入配置 / 审计 / 日志 | 概要设计 §3.2 / §3.10 的不变量清单；两侧各写等价契约测试 |
| **验收标准** | 同一条需求的判定标准两侧共用，不各写一套 | SRS 验收标准列（平台专属判定须在 §10.9 登记） |
| **交互与观感** | 设计令牌（间距 / 圆角 / 字号 / 表面与文本色 / 状态色 / 分类色）取值一致 | 概要设计 §3.9；两侧各有一份令牌表与对比度单测 |
| **文档** | 三书是**唯一共享事实源**，随代码一起进 Git，靠 GitHub 同步 | 本文 + SRS + 概要设计入库；`Scripts/verify-all.sh` 校验 |

**不算「一样」的部分**（允许不同，但必须登记）：菜单 / 快捷键的宿主约定、窗口与停靠行为、字体回退、
原生控件外观、安装与签名方式、终端仿真与 PTY、沙箱与文件授权机制、系统集成（通知 / 深色模式跟随）等。
每一处都进 SRS §10.9 平台差异登记表（P-01 ~ P-12），写清「为什么必须不同」与「用户可感知的差异」。

### 1.1.2 两侧的分工与禁止事项

- **契约向下、实现向上**：概要设计 §3 是两侧都必须满足的接口契约（`【契约】`）；平台实现细节标注 `【macOS】` / `【Linux】`，可自由替换。
- **禁止**：把一侧的库名、类型名、机制名写进需求条目 —— 需求描述必须在两侧都成立。工具会拦（`Scripts/check-platform-neutrality.py`，棘轮只降不升）。
- **禁止**：同一件事有两个真相。需求书 §3/§4 的「状态」列是 **macOS 基线**；Linux 状态只在 `Docs/平台实现状态.json` 登记。
- **禁止**：一侧加能力而另一侧不知情。新增 / 修改 `【契约】` 条目时，等价矩阵与差异登记表必须在同一次提交内更新。

### 1.1.3 当前状态与收敛路径

## 4. 智能体能力专项（本次扩展重点）

### 4.1 现状：内核已具备，缺"暴露 / 深度 / 复用"

已就绪的**治理内核**（均有单测）：接入配置与闸门（`AgentConfiguration` / `AgentGate`）、高危语句分类（`AgentGuardrail`）、逐次审批状态机与审计留痕（`AgentActionGate` / `AgentAudit`）、配额台账（`AgentQuota` / `AgentQuotaLedger`）、自然语言→SQL、specs→数据任务、合成数据。
**这意味着"治理"不是要新建的东西，而是已经存在的资产 —— 规划要做的是让它对外可用、能力更深、可复用。**

### 4.2 三档规划

**A 档｜旗舰（定义产品）**

| 能力 | 是什么 | 为什么闪 | 依赖 |
|---|---|---|---|
| **A1. MCP 作为统一工具接口**（先对内，后对外） | 内嵌智能体的每个动作都走 MCP 工具定义；之后同一套工具可对外暴露给外部智能体 | 与调研书结论一致：「以 MCP 作为对外与对内统一工具接口」。**每个工具调用天然过审批 + 审计 + 配额 + 最小外发** —— 竞品的 MCP 多是裸工具集 | FR-AI-10（🟡 已登记）；**对外暴露按调研书定为进阶可选** |
| **A2. Agent 技能包 + 项目级规则库** | 可版本化、可 diff、可审批的技能（SQL 评审规则、迁移检查表、数据质量探针、命名规范），落进项目目录 | 竞品刚上「AI Agent Skills」的是 IDE 内配置；我们的**技能本身进 git、可审计可回滚** | FR-AI-11（⬜）、工作区 Explorer（待登记） |
| **A3. 「证明再执行」** | 执行前自动：`EXPLAIN` 代价与全表扫描检查 → 事务内真跑再回滚 / `LIMIT 0` → 影响面（命中行数、级联、触发器）→ 输出可读结论，再进审批 | 竞品 AI 给 SQL，我们给 SQL **+ 证据** | 事务 API（FR-EXEC-11/15 🟡）是前置 |

**B 档｜强增益**

| 能力 | 说明 | 依赖 |
|---|---|---|
| **B1. 对话式诊断** | 把执行计划 / 锁等待 / 会话 / 统计喂给模型，产出"为什么慢 + 索引建议 + 反例"，并生成可审批的 `CREATE INDEX` | FR-AI-03（⬜）、FR-DIAG-01/05 已有 |
| **B2. 血缘与影响分析** | 由外键 / 视图 / 函数依赖推导"改这一列会波及什么"，迁移前给影响清单 | 元数据（FR-META） |
| **B3. 迁移成对生成** | 每个 forward DDL 必须配 **rollback**，先在影子 schema 验证再审批执行 | FR-DDL-03/04 |
| **B4. 对抗式复核（双 Agent）** | 一个出 SQL，一个**只找问题**（漏 WHERE、NULL 陷阱、隐式类型转换、锁风险），两份产出都进审计 | 纯编排，成本低 |
| **B5. 终端即工具（受审批）** | 智能体提议 `pg_dump` / `ssh -L`，摊开 → 批准 → 在**内嵌终端**执行 → 留痕 | FR-EDIT-29 已有；**R-18 / T-38 沙箱路线决定其可用性** |

**C 档｜打磨**

零外发可证明模式（外发日志核对）· 成本 / 配额面板与调用回放 · 合成数据安全试跑（FR-AI-07）· 项目级记忆（可检视、**绝不含行数据**）· specs 版本化重跑（FR-AI-11）。

### 4.3 与调研书结论的对应

调研书给的 MVP 必备项（工具调用 / schema grounding / 人在环显式同意 / 工具描述不可信 / 进度取消 / NL→SQL / 诊断 / 过度自主防护 / specs→任务 / 定时调度 / 沙箱导出 / 试运行预览）**在本工程已全部实现**。
本规划的三档**不重复 MVP**，只做调研书里「常用增强 / 进阶可选」的部分，并把其中两处**提前**（A2 技能包、A3 证明再执行）作为差异化。

### 4.4 记忆与自学习层（2026-09-23 讨论收敛，已登记为 FR-AI-13 ~ 15）

**要解决什么**：DBA 的查询工作是重复的 —— 同一批脚本翻来覆去地跑。客户端不该每次都让人从头想一遍：应当从「用户**实际跑过**的 SQL」里长出一条记忆，并**先把补全做扎实**，再谈参数化与主动建议。

**已收敛的四条决定**（需求提出者拍定，逐条已落进 SRS）

| # | 决定 | 说明 |
|---|---|---|
| 1 | **归档 `.sql` 要带元信息** | 元信息以**注释行**随文件保存（连接 / 库 / 首次与最近执行 / 次数 / 耗时 / 影响行数 / 结果 / 说明），语句本身原样内联。**元信息在注释里，所以「编辑器是纯 SQL 编辑器」与「SQL 带元信息」并不冲突** —— 这是本节一个被纠正过的误解：开发助理原先主张"元信息不该进 `.sql`"，实际 `Core/SQLArchive.render` 从 FR-EDIT-31 落地起就是这么写的 |
| 2 | **记忆必须按连接 / 环境隔离** | 记忆的键是连接（连接里已经含环境与登录账号），**每个登录用户有各自的记忆**：生产库的记忆不流进测试库，别人的记忆不流进我的 |
| 3 | **消费顺序：补全 > 参数化 > 主动建议** | 先把「你敲前几个字符就知道你要什么」做到位。**DBA 的重复是「同一批脚本反复跑」，不是「到点自动跑」** —— 定时需求主要在应用侧，所以主动那档排在最后 |
| 4 | **分类与生命周期** | 例行 vs 排障用四个统计量判定（见 H3）；生命周期**按记忆类型分**，不按固定天数一刀切 |

**事实源与派生索引（本节最关键的一条设计）**

归档文件既然是带元信息的、可读可执行的 `.sql`，它就是记忆层**唯一的事实源**；索引（指纹 / 频次 / 参数槽位）是**纯派生缓存，随时可从文件重建**。由此得到三个好处：

- 索引删掉**不丢任何数据**，重建即可 —— 让「索引这一层出错」变成无害的失败；
- **不需要另建侧车日志**，避免「文件和日志谁是真相」的经典纠缠；
- 用户可以用 grep / git 直接检视与版本化自己的记忆（与 P5 可复核同源）。

**流水线（S1 ~ S4）与现状**

| 阶段 | 做什么 | 现状 |
|---|---|---|
| **S1 采集** | 每次执行经 `recordHistory` 单一收口点落成带元信息的归档条目 | ✅ 已完成（FR-EDIT-31） |
| **S2 索引** | 从归档文件派生：粗 / 精指纹、频次、跨天分布、来源连接 | ⬜ 待做（FR-AI-13 的底座） |
| **S3 提炼** | 参数槽位识别、例行候选升格、技能条目生成 | ⬜ 待做（FR-AI-14） |
| **S4 消费** | 补全（第一优先）→ 参数化 → 主动建议 / 定时 | ⬜ 待做 |

> **S2 与「补全」不依赖 D1 ~ D6**：它们只需要本地文件与统计，**没有模型端点也能做、也能测**。真正需要模型端点的只有「由模型生成技能描述」与自然语言部分。

**已知缺口（决定暂不修）**：`SQLArchiveEntry` 只保留首次 / 最近执行时间与当天次数，**每次执行的时刻没有留**。判定「是不是每天 / 每周都跑」—— 跨天文件集合已经够；判定「是不是每天同一时间来、值不值得做成定时任务」—— 需要时刻。**已决定暂不加**，等 S4 确实需要定时建议时再补（改动有 `render → parse` 往返单测兜着）。

**四块硬骨头**（不解决，这一层就会长成「一个越记越乱的提示词堆」）

| # | 硬骨头 | 为什么难 | 倾向 |
|---|---|---|---|
| **H1** | **身份判定：参数化到什么程度仍算「同一条」** | 归一化太松会把语义不同的语句并成一条（补全给出错误候选）；太紧则同一查询碎成几千条（候选全是噪音）。`WHERE id = 1` / `= 2` / `IN (...)` 的列表长度差异怎么算 | 分两级指纹：**粗指纹**（结构骨架，用于聚类与频次）与**精指纹**（原文，用于「同一条」计数）；**补全用粗、计数用精**，两者不混用 |
| **H2** | **隔离边界：跨环境的通用知识怎么在不越界的前提下复用** | 强制隔离会丢掉「命名规范 / Oracle→PG 改写经验」这类与环境无关的知识；放开又会把生产库的库表名带到测试环境 | 记忆分两层：**环境层**（库表名 / 数据分布 / 这条在哪跑的 —— 严格隔离）与**通用层**（方言写法 / 命名习惯 / 改写经验 —— 可跨连接，但**不得携带具体库表名与数据值**，提升前过一道脱敏检查） |
| **H3** | **例行 vs 排障的判别** | 误判代价**不对称**：把一次性排障脚本当例行去定时是**危险**的（可能在生产上按时跑一条从没打算重复的语句）；把例行当排障只是没省事 | 四个统计量取保守侧：**跨天频次 / 跨越天数 / 时刻集中度 / 是否只改参数**。四条**全满足**才升格为「例行候选」，且**升格只产生建议、不自动建任务** |
| **H4** | **遗忘与纠错** | 记忆一旦自动写就会记错（一次误执行的探索性 SQL 会被当成习惯）；用户必须有「这条别记 / 删掉这条 / 为什么记了这条」的入口，且**立即生效** | ① 记忆**不直接写进长期层**，先进候选池、够门槛才升格；② 提供记忆浏览（原文 / 频次 / 来源连接）、单条删除、一键清空、「本次执行不记录」；③ 每次升格与遗忘都留一行**可读理由**（可解释），与 P5 同源 |

**与 Hermes memory 的关系（明确不照抄的地方）**

调研过 Hermes 的做法（`MEMORY.md` 平铺散文 + `§` 分隔、`memory_char_limit` 上限、`write_approval: false`、curator 到 `stale_after_days: 30` / `archive_after_days: 90` 就归档）后，**只借它的"分层记忆 + 定期整理"思路**，三处明确不抄：

1. **不抄 `write_approval: false`** —— 记忆自动落盘且无审批，与 P1 治理优先冲突；
2. **不抄按天数一刀切的生命周期** —— 「一年跑一次但很关键」的巡检脚本会被 30 / 90 天清掉，这正是 DBA 最不能被清的东西；
3. **不抄纯散文存储** —— 散文无法支撑「补全」这种需要结构化检索的消费，故必须有 S2 索引（散文可作为**可读摘要**共存在索引之上，而不是唯一载体）。

## 4.8 连接工程化：SSH 隧道（FR-CONN-18，2026-09-25 已交付）

**为什么值得做**：生产库通常只在内网可达 —— 用图形客户端的人要么先在跳板机上开一个 `ssh -L` 再连本机端口，
要么干脆不用客户端。这件事只有两种做法：让用户自己在外面搭好隧道（产品装作没有这回事），或者把隧道内置。
选后者：连接表单里填跳板机，剩下的事产品做。

**已经交付什么（Core + CLI + 界面 + 脚本）**
  · **参数拼装**：`-N -L 本地:目标`、`ExitOnForwardFailure=yes`、`ConnectTimeout`、`ServerAliveInterval/CountMax`、
    **`UserKnownHostsFile` 指向我们自己的文件**、`ForwardAgent=no`、`IdentitiesOnly=yes`（私钥模式）；
    口令模式关 BatchMode 并把认证限制为口令 / keyboard-interactive。
  · **口令怎么给 `ssh`**：走 **`SSH_ASKPASS`**（0700 临时目录 + 0600 口令文件，握手一结束立刻删），
    不进 argv、不进环境变量本体。**威胁模型如实写清楚**：这是「防别的进程顺手看见」，不是「防同一用户」。
  · **生命周期**：就绪判定（端口探测由调用方注入 —— Core 不许用平台 socket API）、端口被占用时快速失败、
    SIGTERM → 1 秒 → SIGKILL 收场、stderr 尾巴作为诊断依据（口令会被抹掉）。
  · **界面接线**：连接表单里的隧道一段（三种认证方式、指纹策略、超时、逐条参数错误、沙箱提前告知）、
    「测试隧道」（起隧道后真的连一次本机转发端口，把 `ssh → 跳板机 → 数据库`整条走通再收掉）、
    连接时自动起隧道并把目标改写成本机转发端口（改写是 Core 纯函数，`nil` 时一个字段都不改）、
    连接失效 / 删除连接时统一收掉隧道。
  · **绝不碰用户的 SSH 状态**：不动 `~/.ssh/known_hosts`、不动 ssh-agent。一个数据库客户端偷偷改用户的
    SSH 信任库是不可接受的副作用 —— 这是设计决定，不是实现细节。

**什么还没做（如实登记）**
  · **真实跳板机上的握手与认证一次都没跑过**（需要一台可达的跳板机）；
  · **沙箱构建下不可用** —— 沙箱子进程继承沙箱、`ssh` 起不来（R-18 / T-38：与备份恢复同一条分发路线决策）；
    表单里**提前如实告知**，不假装能用；
  · 只支持一个跳板机（不做多级跳板 / ProxyJump 链）、不做 SOCKS 代理、不做隧道健康检查与自动重连。

**证据**：`Tests/SSHTunnelTests.swift` 24 项 + `Scripts/test-ssh-tunnel.sh` 23 项断言（替身 ssh 真起 TCP 转发，
`psql` 通过隧道真连库）+ 界面文案 38 个新键中英齐备。**待人工**：真跳板机 + 界面点击（`Docs/design/待人工验收清单.md` §10.6）。

## 4.9 多库驱动：MySQL 先落地，GBase 8a 在其上（FR-DRV-09 / FR-DRV-08，2026-09-25）

**为什么先 MySQL**：GBase 8a 与 MySQL **同属一个协议族**，而 MySQL 有公开规范、有成熟的
`MySQLNIO`、并且**我能在没有实例的情况下用假服务器把线协议跑起来**。先做 MySQL，等于把
"协议传输 + 方言骨架 + 取消路径"这一层一次性做对；GBase 剩下的就只是版本差异与少量扩展点。

**已经交付什么（MySQL，FR-DRV-09）**
  · `DatabaseType.mysql` + 六处机械补分支（默认端口 3306 / 默认 SSL `prefer` / **没有 schema 层**）；
  · `MySQLService`（`MySQLNIO` 之上）：连接与自省、执行（COM_QUERY 文本协议）、
    **取消**（另一条连接上 `KILL QUERY`，只断语句不断连接）、事务、`COPY` 如实说不支持；
    影响行数**问服务端要**（`ROW_COUNT()` / `LAST_INSERT_ID()`），不自己数；
  · `MySQLDialect`：**转发** `GBaseDialect` 的 MySQL 兼容部分，只改"我是谁"与建库权限探测
    （MySQL 有 `mysql.user`，GBase 没有 → 那边如实返回 nil）；一致性由单测守着；
  · CLI `doyah mysql --sql … [--json]`。

**证据**：11 项方言单测 + `Scripts/test-mysql-driver.sh` **19 项断言**（自写的**假 MySQL 服务器**，
真跑 HandshakeV10 / COM_QUERY / 文本结果集 / ERR 包，验中文、NULL 与空串分得开、影响行数、事务、错误包）。

**什么还没做（如实登记）**
  · **真实 MySQL 实例一次都没连过** —— 认证插件（`caching_sha2_password`）、TLS、字符集协商、
    真实类型、`KILL QUERY` 的权限、NFR-COMP-05 的**多版本窗口**都还没验（脚本已备好：
    `Scripts/test-mysql-real.sh`，无实例时明确报阻塞而不是默认通过）；
  · GBase 8a（FR-DRV-08）**驱动已接上**（组合 `MySQLService` + `GBaseDialect`，`GBaseService`），
    但**真实例端到端 0 次** —— 与 MySQL 同样只有离线证据。最要紧的一处判断是"能力缺口如实留空"：
    GBase 上影响行数显示"未知"，而不是拿客户端自己数出来的数字冒充服务端的；
  · 空结果集的 SELECT 拿不到列定义（MySQLNIO 的 COM_QUERY 路径只在行里带列定义）—— 已知边界。

## 4.10 对话式诊断：把"不许无依据断言"做成机器可判的规则（FR-AI-03，2026-09-25）

**为什么不先接模型端点**：这一条需求的两条硬约束 —— 「结论须引用真实计划 / 统计 / 锁数据，
不允许无依据断言」与「建议可转成 SQL 但须走审批」—— **全部是我们这一侧的判决**，
跟模型是谁、端点在哪没关系。先把它们做成可单测的规则，再换任何模型都仍然成立；
反过来先接端点，就只能在界面上用眼睛看"它今天有没有胡说"。

**已经交付什么**
  · **证据是一等公民**：每份证据有编号（模型引用它）、有**可复跑的取证 SQL**、有三种必须分得开的状态
    （有行 / 零行 / **根本没取到**并写清原因）；取不到的证据在提示词里**单独点名**且写死"不许下结论"。
  · **引用校验**：无依据的结论整条拒绝；编造编号拒绝；**引用"没取到"的证据也拒绝**；
    认不出的行**原样留着**并报"没看懂"（静默丢弃会让用户以为模型没说）。
  · **建议 SQL 走同一道审批闸门**（`ExecutionSafety`）：只读连接上的写语句直接拒绝、高危要求确认。
  · **取数规划是纯函数**，且**执行计划绝不用 `EXPLAIN ANALYZE`**（那会真的执行语句）。

**证据**：16 项单测 + `Scripts/test-diagnosis.sh` 13 项断言（对**真实本机 PG** 取计划 / 锁 / 统计，
模型回复用文件代替）。**一个恰到好处的巧合**：本机 PG 没装 `pg_stat_statements`，
于是"慢查询"证据被如实记成"未取到" —— 这条纪律当场有了活证据。

**界面入口（同日补齐）**：面板**先展示证据**（编号 / 取证 SQL / 没取到的原因标红），再给可复制的资料块，
然后粘贴模型回答并解读 —— 采纳的建议显示安全裁决，「放进编辑器」只写文本不执行。入口三处齐全
（智能体菜单 + ⌘K `diagnoseQuery` + 面板 sheet）。**本机没有端点的用法**：把资料块复制去问任意模型、
再把回答粘回来；自动发问只是把这两次复制换成一个按钮。

**什么还没做（如实登记）**：真实模型端点（本环境没有，提示词与解析都验了，"真的问一次模型"没做）；
慢查询统计要 `pg_stat_statements`（R-42）；面板观感需人工看一眼。

## 4.11 DBA 维护任务编排：审批是前置，不是提醒（FR-AI-04，2026-09-25）

**这一条最容易做歪的地方**：把"一句话生成一串维护命令并执行"当成产品价值。
那样做的用户感受是"点一下，然后不知道它干了什么"。需求原文的三条要求（逐次审批、可预览/可编辑/可拒绝、
高开销限流）其实是在说同一件事：**让维护动作慢下来、看得见**。

**已经交付什么**
  · **解析**：按声明的行格式把计划拆成任务；**认不出的行原样报出来**（维护场景里静默丢一行可能丢掉一个 `DROP`）。
  · **审阅**：写操作 / DDL 一律要审批；索引建议只给语句不要审批；**高开销一次最多一条**（显式开关才放行）；
    **只读连接上的写任务直接拒绝且连批准都不允许**；**沙箱构建下外部程序类任务不可执行**，理由写在任务上。
  · **状态机**：待批 → 已批 / 已拒 → 已执行 / 失败（带服务端原话）；**执行入口只收已批准的任务**。
  · **风险分类复用 `AgentGuardrail`**；备份按 destructive 对待（它动的是整个数据库）。

**证据**：13 项单测 + `Scripts/test-maintenance.sh` 15 项断言（对**真实本机 PG** 真跑 `ANALYZE` 与 `VACUUM`：
没批准一条都没发，批准后才执行）。

**界面入口（同日补齐）**：面板照需求三条排版 —— **逐次审批**（每条一个批准 / 拒绝，刻意不做"全部批准并执行"）、
**可预览 / 可编辑 / 可拒绝**（计划是文本，改完重新审阅；拒绝的留在列表里带理由）、**高开销限流**（默认一条，
跑多条要显式勾"我知情"）；只读连接与沙箱构建两条边界写在面板上。入口三处齐全（菜单 + ⌘K + sheet）。

**什么还没做（如实登记）**：真实模型端点；"就地编辑某一条任务"的界面（当前改计划文本后重新审阅）；
GBase / MySQL 上的维护语句（`VACUUM` 系是 PG 专属）；面板观感需人工看一眼。

## 4.12 MCP 双向：先把报文与权限判据做对，再谈接谁的服务器（FR-AI-10，2026-09-25）

**为什么先做协议层与权限判据**：MCP 的互操作价值取决于两件事 —— 报文对不对、**权限有没有真的继承当前会话**。
这两件事都不需要真实 MCP 客户端 / 服务器在场就能验（假对端足够），而"接上某某客户端"恰恰是最后一步。

**已经交付什么**
  · 两个方向**共用一套 JSON-RPC 报文**（同一份解析与生成，因此不可能两个方向不一致）；未知字段保留、坏报文 `-32700`、
    未实现方法 `-32601`、协议版本不一致时如实回报我们支持的版本。
  · 暴露四个工具（查询 / 对象列表 / 表结构 / 导出），**刻意不暴露**连接管理与口令、备份恢复与维护任务、工作区文件读写。
  · **不另开特权**：能力从当前连接推导、外部请求改不了；没会话就一律拒；只读连接上的写语句被拒且批准也不能绕过。
  · **按次审批**：写语句即使在只读工具里也要审批；批准单位是"这一次调用"。
  · 每次调用进审计（可落盘 JSONL）。

**一个被脚本抓出来的漏洞（值得记下来）**：最初审批按**工具名**算，于是"允许 `query_sql`"等于允许通过它下发**任何**语句 ——
实测真的把 `DELETE FROM customers` 下发了，只是被外键挡下。改成**按次**（工具名 + 参数指纹）之后，
"逐次审批"才是逐次审批。**没有假对端脚本，这个漏洞会一直躺在代码里直到某天真删了数据。**

**证据**：20 项单测 + `Scripts/test-mcp.sh` 13 项断言（假 host 驱动我们的 server：真连 PG 跑查询、真下发一条被批准的写语句、审计 11 条；假 server 驱动我们的 host）。

**界面审批通道（同日补齐）**：MCP server 跑在 CLI 的 stdin/stdout 上（协议通道，借不来弹窗），
所以两侧共用一个**文件队列**：server 入队并等，面板显示待审批项（**要执行的 SQL 摆最显眼处**），
人点允许 / 拒绝写决定，server 读决定再执行。三条口径：**批准只对这一次有效**（指纹级）、
**没人确认时默认不放行**（超时 = 拒绝）、队列位置可见。

**又一次被脚本抓到的缺陷**：配了队列时会话先回"需要审批"、批准后再回结果 —— **一个请求两个响应**，
违反 JSON-RPC，客户端会把真结果当成多余报文丢掉。改成"配了队列就先不回，点完只回一个"。

**什么还没做（如实登记）**：host 方向是批处理式最小闭环（不做长连、不处理服务器反向请求）；
未接真实 MCP 客户端 / 服务器；资源只做了 `resources/list` 的最小实现；面板观感需人工看一眼。

## 8. 复评机制

- **触发**：每个里程碑结束、或每季度一次；需求提出者提出新方向时立即复评。
- **动作**：① 用 SRS 重新派生能力地图（本文件第 2 节）；② 检查依赖表 D1～D6 有无变化；③ 调整三档顺序并在文末追加一行；④ 若某能力的**实现已完成但长期卡在验收**，在依赖表里标注，而不是留着假装在推进；⑤ **双平台视角复评**：核对 §10.10 等价矩阵与 §10.9 差异登记表 —— 新登记的能力是否两侧都排上了、新出现的平台差异是否登记了理由、中立性负债是否只降不升。
- **纪律**：**未实测的能力不得标记为达成**（与 NFR-COMP-03 / 05 同一纪律）；**未登记的差异不算差异，只算漂移**（P7）。
